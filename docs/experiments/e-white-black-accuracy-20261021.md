# 現行EのPP-OCRに白・黒抽出を適用した99画像の精度比較

**今回の固定条件では、白・黒抽出の併用で現行Eの精度は改善しなかった。** 現行EのCERは7.07%、白黒二候補から選ぶ方式は8.76%、原画像も候補に残す方式は7.50%。原画像を残しても、現行Eより改善1枚・悪化13枚・同じ85枚だった。通常アプリのEは変更しない。

同じ非公開の実動画由来99画像・2,545正解文字を使い、Android上で各条件を3反復した。原画像の出力は保存済みEの全99画像と毎反復一致し、字幕bandの位置・粗認識文も一致した。5条件の最終出力は3反復とも一致した。公開するのはこの分析と[集計JSON](e-white-black-accuracy-20261021/summary-only.json)だけで、元画像・正解文・OCR全文・画像別ID・APKは公開しない。

## 変更した部分と固定した部分

原画像のEを先に実行し、その処理から得たML Kitの検出行と字幕bandを各条件で共用した。ML Kitの粗認識、strip recovery、Eの背景除外、band選択、band拡大、refine時のML Kit検出、行cropの余白・隣接行境界を固定する。変えるのは、**PP-OCR v6 Smallの各行認識へ渡す画素**と、複数候補から認識結果を選ぶ部分だけである。

- 原画像：既存の`V6ComparisonOcrEngine.refineRecognized()`をそのまま呼んだEを基準とする。
- 白抽出：各行cropでRGB最小値≥210、最大値−最小値≤45の画素を黒、それ以外を白。既存`whiteCore()`と同じ規則。
- 黒抽出：各行cropでRGB最大値≤45、最大値−最小値≤45の画素を黒、それ以外を白。
- 白黒選択：白・黒を別々にPP-OCRで認識し、正規化後に片方だけ非空ならその候補、両方非空ならCTC平均信頼度が高い候補を選ぶ。同点は白、両方空も白。
- 原画像＋白黒選択：同じ規則で原画像候補と白黒選択候補を比較し、同点は原画像を残す。

しきい値と選択規則、ハーネス・モデル・辞書・APKのSHAを最初の推論前に凍結した。**正解文はAndroidへ転送せず、検出・選択・認識へ渡していない。** Mac側で入力manifestと全PNGのSHAを既存比較スクリプトで検証し、同じ正解データと`comparisonKey`で採点した。

候補を選んだ後は、既存の`PpOcrRefinementPolicy`と`OcrRefinementSelector`、`ECaptionOcrPolicy`を適用する。PP候補が条件を満たさない場合のML Kitへのfallbackも残す。これはPPの生の全文を連結した認識率ではなく、**Eの採用条件を通った最終字幕の精度**である。

原画像Eで発生した白抽出の追加refineは2回あり、各条件でも同じ実行予定・同じ検出位置を使った。この追加refineの行cropも、それぞれの条件の画素変換を適用する。候補の変化を理由とした新たな検出や追加再試行は行わない。通常アプリを変更した場合の動的な再試行全体を測る試験ではない。

1反復の処理対象は93 band・95 refine呼出・223 PP行入力。前回のIndra診断は保存済みの粗行214個を使っており、本試験と認識器入力の矩形は異なる。二つの実験の数値だけから、認識器単体の優劣は結論しない。

## 候補が増えても改善しなかった理由

223行入力のうち、白黒選択は白198行・黒25行を選んだ。原画像を残す方式では原画像134行・白86行・黒3行を選んだ。**同じ認識器のCTC信頼度で比較しても、画素変換が異なる候補間で、信頼度が高いほど正しいとは限らなかった。** 最終字幕で改善1枚・悪化13枚という結果が、この選択規則の限界を示す。

既存PP置換条件を満たした行は、原画像215、白193、黒81、白黒212、原画像＋白黒215だった。抽出画像だけにすると、PP候補が採用条件を満たさなくなる場合もある。逆に、採用条件を満たした変換候補でも文字列が誤る場合がある。条件を満たす行数が同じでも、最終精度は保証されない。

この試験では位置が固定されているため、上記の精度低下は字幕位置を見失ったことによるものではない。画素変換後の認識結果と候補選択・採用処理の違いとして観測した。Indraで白抽出が有効だった結果を、PP-OCRを使うEへそのまま一般化することはできなかった。

参考として、正解を使って**画像ごとに今回の5方式の最終出力から最良を選ぶ**診断では177 edits・CER 6.95%・完全一致78枚となる。これは現行Eより3 edits少ないだけであり、実装可能な選択規則ではない。行単位や文字単位の任意の組合せまで含む上限でもない。

## 確認と限界

- 原画像Eの最終出力、band位置、粗認識文を保存結果と全99枚×3反復で照合した。行cropとPP置換結果の手動再構築も、既存の実装の文字列・backend・probability・矩形と一致した。
- Mac側の全1,485組（99枚×5方式×3反復）の採点を、製品のJava `SubtitleNormalizer`・`Similarity`を直接実行して独立に検算した。
- 環境はApple M4 / 16GiB上のAPI36 ARM64専用エミュレーター、ML Kit Japanese16.0.1、ONNX Runtime Android1.30.0、PP-OCR v6 Small、既存と同じモデル・辞書。PP入力・CTC復号も製品の実装を使用した。
- 実行は2026-10-21 10:12:04〜10:14:40 JST。モデルSHAは`5435fd747c9e0efe15a96d0b378d5bd157e9492ed8fd80edf08f30d02fa24634`。その他の固定SHAは集計JSONに保存した。
- 既知の3動画での探索結果であり、heldout区分も過去に使用済み。正解は既存の画素確認による転記を共用し、新たな人手監査と未知動画での評価は実施していない。
- 今回は精度の比較で、方式別の全体速度は測っていない。原画像の検出を共用し、同じ候補の認識結果を選択方式間で共有するため、内部の部分時計を方式別のfull pipeline時間として扱わない。

**現時点では、白黒候補を追加する方式を通常Eへ採用する根拠は得られなかった。** テスト専用の一時変更は実行後に戻し、アプリ本体・既存E・既存テストソースに変更は残していない。画像、正解文、個別結果、実行ハーネスはMac内だけに保持する。
