# Mac実測：非公開99画像でIndra OCR 1.1.2と現行Eを比較

**結論：今回の日本語字幕用途では現行Eを維持する。** 2026-10-20、Mac保存済みの実動画由来99画像について、PR #64の比較スクリプトでIndra通常設定・正立指定（`turn=False`）を各画像3回、合計594回実行した。CERはE **7.07%**、Indra通常 **76.03%**、正立指定 **72.93%**。通常アプリのコード・E方式・設定は変更していない。

数値のみの出力：[元スクリプトの集計](indra-e-mac-private99-20261020/summary-only.json)、[E保存時間・反復・背景混入の追加集計](indra-e-mac-private99-20261020/analysis-only.json)。元画像、正解文、OCR全文、画像別ID・時刻、モデルは追加公開していない。

**原因の追試：** [字幕位置と文字認識を分離した診断](indra-detection-vs-recognition-20261020.md)では、Eの位置だけへ置換してもCER 58.00%が残り、背景・縁取りへの認識側の弱さを確認した。白文字抽出＋CJK固定を加えると実99画像で9.86%まで改善したが、主試験とは別の探索条件であり、通常アプリは変更していない。

## 入力と比較条件の確認

- 実行コードはPR #64のcommit `38fe5960a20cf24502f15884486c0ddb231d52ef`にある[`private99_compare.py`](../../tools/indra-ocr-research/private99_compare.py)。変更せず、`--threads 4 --repeat 3`で使用した。元データを使わない同PRのユニットテスト4件も成功した。
- `dev-cat` 28枚、`dev-watch` 28枚、`heldout` 43枚の元`dataset.json`のSHAが、スクリプト内の凍結値3件と一致。全99 PNGのbytesのSHAも一致した。再収録・合成・代替画像は使っていない。
- Eの保存済み初回JSONと全99画像の正解文・frame ID・時刻が一致。Pythonで再計算した各画像の編集距離と正解文字数がAndroid保存値に一致し、**180 edits / 2,545文字**を復元した。追加集計ではEの保存済み第2・第3反復も同じ条件で照合し、全出力の一致を確認した。Eは今回再推論していない。
- Indraには同じ元フレーム全体をPillowで8bitグレースケール化して入力。全出力行を順に連結し、Eと同じ正規化・比較キーで採点した。GTによる行選び、字幕ROIへの切り出し、文字列修正、画像ごとの設定選択は行っていない。
- 3反復は画像ごとに「通常設定を3回→正立指定を3回」の順で、同一プロセス・同一ロード済みモデルを使う。各設定のOCR文字列は3回とも一致し、方向情報にも反復差はなかった。99枚を別プロセスで3周する試験ではない。

## 精度と字幕の取り逃し

CERは全画像の編集距離合計÷正規化後の正解2,545文字。完全一致も正規化後の比較であり、句読点・空白等を含めたbytesの一致ではない。字幕あり87枚、字幕なし12枚を共通の分母に使う。

|E 保存済み|180|7.07%|77|77.78%|2（2.30%）|3（25.00%）|
|Indra 通常|1,935|76.03%|18|18.18%|11（12.64%）|6（50.00%）|
|Indra 正立指定|1,856|72.93%|21|21.21%|10（11.49%）|6（50.00%）|

## 回転判定と背景混入の分析

通常設定は`dev-watch`の3枚を180度回転した。この3枚の編集数は通常79→正立指定0となり、3枚とも完全一致になった。全体の差79 edits（CER 3.10ポイント）はこの3枚に対応し、残り96枚のOCR全文は両設定で同じだった。正立指定でも猫・移行動画の全71枚に完全一致はなく、回転誤判定を避けるだけではEとの差は解消しない。小角度の傾き補正量は全99枚で0だった。`turn=False`は方向モデルによる90/180度等の回転判定を止める指定であり、1.1.2の傾き補正処理そのものは引き続き動く。

時計動画だけでは正立指定のCER 6.76%がEの8.54%を下回る一方、完全一致は21枚対26枚、字幕なしでの誤出力は2枚対0枚だった。CERだけで全画像の安定性を判断しない。99枚全体で画像ごとの編集距離を比べると、通常設定はEより良い2・同じ20・悪い77枚、正立指定は良い2・同じ23・悪い74枚だった。

既存の非字幕文字boxの注釈がある40枚で、背景ラベルの正規化文字列がGTより余分に含まれるかを同じ条件で照合した。該当はE **3/40**、Indra両設定 **8/40**（猫ではE 1/11、Indra 7/11）。例えば、字幕とは別の名札が出力へ残る種類の誤りをこの診断で確認した。正解文・名札の実文字列・画像は公開しない。この文字列照合は全背景誤りの網羅的な画素監査ではなく、未注釈59枚を混入0件と扱わない。

Eには字幕候補選別がある一方、今回のIndraは全画面OCRで、背景の文字も字幕出力へ加わり得る。したがって今回の数値は**字幕リーダーへそのまま使う経路の比較**であり、検出モデル単体・認識モデル単体の差や、その因果内訳を確定する試験ではない。

## 処理時間

**MacネイティブIndraと、保存済みAndroidエミュレーターEの時間を独立に表示する。速度倍率やGalaxy実機の速度へ換算しない。**

|区分|E 既存Android warm 中央値 / p95 ms|Indra 通常 Mac 中央値 / p95 ms|Indra 正立指定 Mac 中央値 / p95 ms|
|---|---:|---:|---:|
|dev-cat|311.00 / 507.00|65.47 / 82.14|57.36 / 70.41|
|dev-watch|149.00 / 193.00|47.90 / 64.93|37.63 / 63.99|
|heldout|237.00 / 367.00|65.88 / 85.31|59.30 / 76.03|
|全体|237.00 / 373.00|62.24 / 85.22|51.83 / 75.01|

- IndraはPRスクリプトどおり各画像の第2・第3呼び出しの中央値を取り、その99個の中央値・nearest-rank p95を示す。p95は個々の全呼び出しのp95ではない。モデルload **1,139.74ms**と画像decodeはこの時計外で、`conv.ocr()`全体を`perf_counter`で測った。
- Eは保存済み3反復からframe0とlazy-init増分のある画像を除外し、285 warm観測（猫81・時計78・移行126）をpoolした。既存集計の中央値/p95と一致する。Android時計は`elapsedRealtime`、粗OCR・候補選別・crop・refine・E選別・診断構築を含み、decode・転送・capture待ち・TTS待ちを含まない。
- Indra全594呼び出しの計測時間合計は**34,348.813ms**（通常18,208.864ms、正立指定16,139.949ms）。起動・load・decode・採点等を除くOCR呼び出しの合計である。

Indraの3回を個別に見ると以下のとおり。各列は同じ99枚の同じ反復番号を集計したもの。

|設定|第1回 中央値 / p95 ms|第2回 中央値 / p95 ms|第3回 中央値 / p95 ms|
|---|---:|---:|---:|
|通常|57.13 / 79.07|61.02 / 83.54|63.21 / 86.78|
|正立指定|54.16 / 76.44|52.57 / 77.00|51.88 / 75.05|

参考に第2・第3呼び出しを画像内中央値にせず198観測としてpoolすると、通常62.071 / 85.819ms、正立指定52.435 / 75.046ms。猫の正立指定には230.272msの呼び出しもあり、画像内中央値を使う主表だけでは個々の遅い呼び出しを十分に表せない。全呼び出し・反復別・区分別の数値は追加集計JSONに保存した。

## 環境・再現方法・限界

実測時刻は2026-10-20 **17:52:40〜17:53:19 JST**（ログの作成〜最終更新を秒単位で外側へ丸めた範囲）。MacはApple M4 / 16GiB、macOS 26.6.2、Python 3.14.4、ONNX Runtime 1.31.0、NumPy 2.5.4、Pillow 12.3.0、OpenCV headless 5.0.0.93、4 threads。測定前はAC接続で温度・性能警告の記録なし。測定中の実CPU温度・消費電力・他プロセス負荷は計測・統制していない。

Indraのパッケージは**1.1.2**。同パッケージが指定するモデルはHugging Face `datalab-to/indra-ocr`の**v1.1.0**（commit `bd02167fdf2005a19962cc15188f8496a2c87d3b`）で、パッケージ番号とモデルtagを混同しない。モデルは先にダウンロードし、推論時はローカルモデル指定と`HF_HUB_OFFLINE=1`を使用。モデルファイルSHAと主要依存versionを追加集計JSONへ記録した。

再現は[PRの手順](indra-e-mac-private99-plan-20261020.md)の入力を実在する非公開保存先へ設定して実行する。

```sh
INDRA_OCR_MODEL_DIR="$LOCAL_MODEL_DIRECTORY" HF_HUB_OFFLINE=1 HF_HUB_DISABLE_TELEMETRY=1 \
  .venv/bin/python tools/indra-ocr-research/private99_compare.py \
  --datasets "$DATASETS" --e-results "$E_RESULTS" \
  --private-output "$PRIVATE_OUT/raw" \
  --public-summary "$PRIVATE_OUT/summary-only.json" --threads 4 --repeat 3
```

集計値の追加検証では、保存済み9件のE JSONの正解・ID・時刻・編集距離・反復出力一致を確認し、既存[`cold_indices` / `timing`](../../tools/bd-retest/analyze.py)でwarm時間を再集計した。背景診断は既存[`metric`](../../tools/bd-retest/analyze.py)と同じ注釈・文字列照合条件を使った。ローカル補助集計コードと全文データはGit管理外に保存し、GitHubへは匿名の区分別集計だけを追加した。

正解文は以前の実験で画素から転記されたもので、人による監査は引き続き未完了。3動画は既知素材であり、`heldout`も未使用の独立検証素材ではない。Galaxy S25の推論、長時間動作、ライブ字幕の取り逃しや可聴遅延は未測定。今回の結果でIndraを通常アプリへ組み込む根拠は得られず、現行Eを維持する。
